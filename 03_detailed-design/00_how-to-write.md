# 詳細設計の書き方・粒度ルール

> 詳細設計は「AIエージェント・開発者がこれを読めば、迷わず実装できる」粒度で書く。
> 概要設計（`../02_architecture`）が WHAT/全体なら、詳細設計は HOW/各部品。

## 1. 原則
1. **1つの実装対象 = 1ドキュメント**（1テーブル / 1エンドポイント / 1画面 / 1バッチ）。テンプレートを使う。
2. **要件IDと紐づける**。各詳細設計は、どのFR/NFRを満たすかを明記（トレーサビリティ）。
3. **曖昧さを残さない**。入力・出力・エラー・境界値・制約をすべて書く。空欄＝未決定として実装しない。
4. **概要設計と矛盾しない**。矛盾に気づいたら、まず上流を直して合意し直す。

## 2. ディレクトリと対応
| 対象 | 置き場所 | テンプレート |
|------|---------|------------|
| DBテーブル | `db/`（ドメイン別フォルダ推奨） | `db/templates/table-template.md` |
| APIエンドポイント | `api/` | `api/templates/endpoint-template.md` |
| 画面 | `screen/` | `screen/templates/screen-template.md` |
| バッチ / 非同期 | `batch/` | `batch/templates/batch-template.md` |

## 3. 命名・ID付与
- ドキュメントIDは対象のIDに揃える（テーブル名、エンドポイントID、画面ID、バッチID）。
- ファイル名例: `db/auth/auth_users.md`、`api/auth/login.md`、`screen/scr-010-user-management.md`。

## 4. 粒度の目安（Doneの判断）
詳細設計は、以下を読み手が判断できて初めて「書けた」とする。
- [ ] 入力（型・必須・制約・バリデーション）が確定している
- [ ] 出力（成功・失敗の形）が確定している
- [ ] 処理ロジック・分岐・計算式が確定している
- [ ] エラー・例外・境界値の挙動が確定している
- [ ] 認可（誰が実行できるか・データ所有権）が確定している
- [ ] 関連する要件ID・テーブル・API・画面が参照されている
- [ ] テスト観点が書かれている（`../04_quality`）

## 5. 変更時
詳細設計の変更も、上流に影響するなら変更管理フロー（`../08_process/03_change-management.md`）に乗せる。
軽微な実装レベルの明確化はADR不要だが、設計意図の変更はADR化する。
