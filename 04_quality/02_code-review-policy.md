# コードレビュー方針（人間 & AI）

> 大規模ゆえ全コードを人間が精読するのは非現実的。**レビュー対象の優先度付け**と
> **人間/AIの役割分担**で、重要な箇所に人間の目を集中させる。

## 1. レビューの目的
1. 要件・設計との整合（仕様通りか）
2. セキュリティ（認可・入力検証・機密情報）
3. 保守性（規約順守・可読性・責務分離）
4. テストの十分性

## 2. 人間とAIの役割分担
| 観点 | 1次（AI/自動） | 最終判断（人間） |
|------|:-------------:|:---------------:|
| 整形・規約 | ✓（lint/formatter） | — |
| 静的解析・バグ検知 | ✓ | 重要指摘のみ |
| セキュリティ観点 | ✓（補助） | ✓（必須） |
| 要件・設計整合 | ✓（補助） | ✓（必須） |
| アーキ影響・意思決定 | — | ✓（必須） |

- AIは広く速くチェックし、人間は「判断が必要な箇所」に集中する。
- **セキュリティ・認可・アーキに関わる変更は人間レビュー必須**。

## 3. レビュー優先度（リスクベース）
全PRに同じ労力をかけない。リスクで優先度を分ける。

| リスク | 例 | 人間レビュー |
|--------|-----|------------|
| 高 | 認証/認可、課金、データ削除、スキーマ変更、外部公開API | 必須・複数人推奨 |
| 中 | 主要業務ロジック | 必須 |
| 低 | 表示文言、軽微なUI、ドキュメント | AI + 軽い確認 |

## 4. レビュー観点チェックリスト
- [ ] 対応するFR/設計IDが明記され、仕様通りか
- [ ] 認可・データ所有権が正しく適用されているか
- [ ] 入力バリデーション・出力エスケープがあるか
- [ ] 機密情報のハードコードがないか
- [ ] SQLがプレースホルダ/ORM経由か
- [ ] テストが追加され、観点を網羅しているか
- [ ] 命名・規約（`rules.md`）に従っているか
- [ ] 設計ドキュメントの更新が必要なら更新されているか

## 5. 運用
- PRは1目的・レビュー可能なサイズ（大きい変更は分割）。
- PRテンプレートに「対応FR」「変更概要」「テスト内容」「影響範囲」を記載。
- 指摘は {{must / should / nits}} でラベリングし、must は解消必須。
