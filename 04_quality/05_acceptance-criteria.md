# 受け入れ基準（Doneの定義）

> 「完了」の意味をチーム・顧客で揃える。曖昧な「できた」をなくす。
> Definition of Done（DoD）を機能・フェーズの各レベルで定義する。

## 1. 機能レベルの Done（Definition of Done）
1つのFR/機能が「完了」と言える条件:
- [ ] 詳細設計が `Agreed`（または設計通り実装されている）
- [ ] 実装が完了し、対応FR/設計IDが紐づいている
- [ ] ユニット/統合テストが追加され、テスト観点を網羅している
- [ ] 認可・データ所有権のテストが通っている
- [ ] 静的解析・整形・脆弱性チェックがグリーン
- [ ] カバレッジ基準を満たす
- [ ] レビュー（必要に応じ人間）承認済み
- [ ] 受け入れ基準（下記）を満たすことを確認
- [ ] トレーサビリティ表のステータスを更新した

## 2. 受け入れ基準の書き方（Given/When/Then）
各FRに紐づけて記述する。顧客・テストと共有できる形にする。

```
シナリオ: {{シナリオ名}}
  Given {{前提条件}}
  When  {{操作}}
  Then  {{期待結果}}
```

### 例: FR-AUTH-001 ログイン
```
シナリオ: 有効なユーザーがログインできる
  Given 有効なアカウントが発行されている
  When  正しい認証情報でログインする
  Then  ホーム画面に遷移し、監査ログに記録される

シナリオ: 無効なアカウントは拒否される
  Given アカウントが停止されている
  When  正しい認証情報でログインする
  Then  ログインは拒否され、理由が表示される
```

## 3. フェーズレベルの Done
- [ ] 当該フェーズのスコープ内FRが全て Verified
- [ ] 非機能要件（性能・セキュリティ）の確認が済んでいる
- [ ] ステージングで受け入れテストを実施し顧客が確認した
- [ ] 既知の未解決課題が整理され、リリース可否が合意されている

## 4. リリースの Done
- [ ] 本番相当環境での最終確認
- [ ] ロールバック手順の確認
- [ ] 監視・バックアップの稼働確認
- [ ] 顧客のリリース承認（`../08_process/02_agreement-flow.md`）

## 5. 受け入れテストの進め方
- 顧客と一緒に、受け入れ基準（Given/When/Then）に沿って確認する。
- プロトタイプ・ステージングを使い、認識齟齬を早期に解消する。
- 合意結果は議事録・チェックリストで記録に残す。
