# トレーサビリティ（要件 ↔ 設計 ↔ 実装 ↔ テスト）

> 人間が全コードを把握できない前提で、**「どの要件が、どこで実装され、どのテストで検証されているか」**を
> 機械的に追えるようにする。これが抜けると「作ったつもり / 直したつもり」を検知できない。

## 1. 追跡の鎖
```
FR-xxx（要件） → 設計ドキュメント → 実装（PR/コミット） → テスト（テストID） → Verified
```
各成果物に要件IDを埋め込むことで鎖をつなぐ。
- 設計: 各ドキュメントの「関連FR」。
- 実装: PR説明・コミット・コードコメントに `FR-xxx` を記載。
- テスト: テスト名 or タグに `FR-xxx` を含める。

## 2. トレーサビリティ・マトリクス（RTM）
全FRの実装・検証状況を一覧化する。リリース前に全行が `Verified` になることを目標とする。

| FR-ID | 要件名 | 設計Doc | API | テーブル | 実装PR | テストID | ステータス |
|-------|--------|---------|-----|---------|--------|----------|-----------|
| FR-AUTH-001 | ログイン | 02_auth-and-access | AUTH-login | auth_users | #PR | T-AUTH-001 | {{Draft/実装中/Verified}} |
| FR-AUTH-002 | ユーザー発行 | 02_auth-and-access | USER-create | auth_users | | | |
| | | | | | | | |

> 可能なら、この表はコード・テストのタグから半自動生成する仕組みを用意する。

## 3. ステータス定義
| ステータス | 意味 |
|-----------|------|
| Draft | 要件のみ存在 |
| Designed | 設計完了 |
| Implemented | 実装完了（テスト未） |
| Verified | テストで検証済み・受け入れ基準達成 |

## 4. 運用ルール
- PRマージ時に、対応するFRのステータスを更新する。
- 「対応FRのないコード変更」は原則禁止（リファクタ・基盤整備は例外として明記）。
- リリース判定会でRTMをレビューし、未検証要件がないか確認する。
